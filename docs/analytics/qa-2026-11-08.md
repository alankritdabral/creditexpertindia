# Final verification — 2026-11-08

Phase 11 of plans/01-visibility-and-analytics.md. This repo's sandbox has
no live Firebase project, Upstash Redis, MessageBot credentials or real
GA4/Clarity property, so the checks below are everything that could be
verified without those — a static build, source inspection, and curling a
local production server. The items that need a live environment and a real
phone number are listed at the end as a script for a human to run before
this ships.

## 1. Documentation conformance

- Every `gtag` call in the codebase (`lib/analytics/*`, `app/layout.tsx`,
  `instrumentation-client.ts`, `components/analytics/*`) uses only the
  commands confirmed in Phase 0's research: `config`, `get`, `set`,
  `event`, `consent`. No invented command.
- `window.clarity` calls go through `lib/analytics/track.ts` or
  `lib/analytics/clarityTags.ts` only, and `components/analytics/Clarity.tsx`
  always calls `consentV2()` with explicit arguments.
- JSON-LD is built from `lib/structuredData.ts`'s `jsonLd()` escape helper
  everywhere it's used (checked by grep: every `dangerouslySetInnerHTML`
  rendering `application/ld+json` in `app/` and `components/` calls
  `jsonLd(...)`, except the calculator page's still-manually-maintained
  block, which also goes through `jsonLd()` — see its own code comment on
  why that one isn't data-driven).

## 5. What this did NOT verify (needs a human, a phone, and live credentials)

This sandbox has no real Firebase project, Upstash Redis, MessageBot
account, GA4 property or Clarity project, so none of the following was
exercised end to end. Before relying on this in production, someone with
access to those should walk through:

1. Arrive at the site from a tagged link, e.g.
   `https://www.creditexpertindia.com/?utm_source=qa&utm_medium=e2e`.
2. Accept analytics and recordings in the consent banner.
3. Open GA4 DebugView (via the Tag Assistant extension) and confirm, for
   each funnel, the expected event sequence fires in order with no
   personal data in any parameter (search the raw request payloads for
   the test mobile number and PAN — expect zero hits):
   - **Eligibility:** `lead_form_view` → `lead_form_start` →
     `lead_form_submit` → `otp_request` → `otp_sent` → `otp_verified` →
     `generate_lead` → `credit_report_fetch` → `credit_report_view`.
   - **Contact:** `lead_form_view` → `lead_form_start` →
     `lead_form_submit` → `generate_lead`.
   - **Calculator lead:** modal open (`lead_form_view`) →
     `lead_form_submit` → `generate_lead`.
4. Deliberately trigger each wrong-path case once and confirm exactly one
   `lead_form_error`/`otp_failed` fires with the right code: wrong OTP,
   expired OTP, invalid PAN, missing consent, salary below the minimum.
5. In Firestore, confirm the lead/credit_reports document has an
   `attribution` object with the test UTM values, a `consent` object, and
   (for contact/calculator-lead) that `lead_analytics` has a matching
   record with **no** name, phone, or PAN in it.
6. If Clarity is configured (`NEXT_PUBLIC_CLARITY_ID` set): confirm a
   recording exists, the credit-report dashboard and the OTP modal are
   masked in it, and it can be found by its `lead_ref`/`ga_client_id` tag.
7. Submit each lead form with required consent unchecked and confirm the
   server rejects it (400) rather than saving anything.
